## Source Tree

The UDUNITS-2 source tree contains the library, command-line utility, tests, build configuration, and units database.

The primary development directories are:

| Directory       | Contents                                                                   |
| --------------- | -------------------------------------------------------------------------- |
| `lib/`          | UDUNITS-2 library source, public headers, unit database, and library tests |
| `prog/`         | `udunits2` command-line utility                                            |
| `test/`         | Development build and verification scripts                                 |
| `conda.recipe/` | Conda package configuration                                                |

The top-level build files support both GNU Autotools and CMake builds.

## Development Prerequisites

A development build requires a C compiler and the Expat XML parser.
The project also uses the following tools depending on the build and development task:

- GNU Autotools for regenerating the Autotools build system
- CMake for CMake builds
- Flex and Bison for regenerating the parser and scanner sources
- CUnit for running the unit tests
- Texinfo for regenerating the documentation

CUnit is optional.
When it is not available, the library can still be built, but the CUnit-based tests are disabled.

## Building with Autotools

The Autotools build system is used by the standard source-build workflow.

For a Git checkout, regenerate the build system when necessary:

```bash
autoreconf -fi
```

Configure a development build with debugging enabled:

```bash
./configure --enable-debug
```

Build the library and command-line utility:

```bash
make
```

The `--enable-debug` option enables debugging support and builds without optimization.

For the complete set of configuration options, see [Configure Script Options](configure-options.html).

## Building with CMake

UDUNITS-2 also provides a CMake build system.

Create a separate build directory and configure the project:

```bash
cmake -B build -S .
```

Build the project:

```bash
cmake --build build
```

The project uses C99 and builds a shared library by default.
CMake also supports platform-specific Windows builds, including builds with Visual Studio.

A specific compiler and build type can be selected when configuring:

```bash
cmake -B build \
    -DCMAKE_C_COMPILER=clang \
    -DCMAKE_BUILD_TYPE=Release \
    -S .
```

## Regenerating Parser and Scanner Sources

The unit expression parser uses generated C source files.

The source tree contains:

- `lib/parser.y` — Bison parser definition
- `lib/scanner.l` — Flex scanner definition
- `lib/parser.c` — generated parser source
- `lib/scanner.c` — generated scanner source

When developing changes to the parser or scanner, regenerate the generated sources using Bison and Flex:

```bash
cd lib
flex -d -Put -o scanner.c scanner.l
bison -t -p ut -o parser.c parser.y
```

The CMake build can regenerate these files on Unix systems when Flex and Bison are available.

## Regenerating Grammar Documentation

The canonical unit-expression grammar is maintained in `GRAMMAR.md`.

The library documentation includes a generated `grammar.texi` file derived from `GRAMMAR.md` using `lib/md-grammar-to-texi.awk`.

When the grammar source or conversion script changes, the generated documentation can be regenerated by the build system.

## Running Tests

The project uses CUnit for its library unit tests.

With an Autotools build, run the test suite with:

```bash
make check
```

When CUnit is available, the library's test programs are built and executed as part of the test suite.
The tests use the source-tree XML database through `UDUNITS2_XML_PATH`.

With a CMake build:

```bash
cmake --build build
cd build
ctest
```

The CMake build registers the `testUnits` test when CUnit is available.

## Development Checks

The source tree includes a development makefile that performs broader build checks.

Run the development checks with:

```bash
make -f dev-makefile check
```

These checks exercise both supported build systems and multiple compilers.
The development workflow includes:

- Autotools builds with `cc` and `clang`
- CMake builds with `cc` and `clang`
- Building, testing, and installing the CMake build
- Creating a package from the CMake build

The top-level `check` script invokes this development check workflow.

## Debugging Tests

The Autotools build provides targets for debugging the CUnit test programs with GDB.

For the Version 2 API tests:

```bash
make -C lib debug-2
```

For the legacy Version 1 API tests:

```bash
make -C lib debug-1
```

The test programs are run with the source-tree units database selected through `UDUNITS2_XML_PATH`.

Valgrind checks are also available for the test programs:

```bash
make -C lib valgrind-2
```

## Development Workflow

A typical development cycle is:

1. Modify the source code.
2. Regenerate generated sources if necessary.
3. Build the project.
4. Run the test suite.
5. Run the broader development checks when appropriate.
6. Review the changes and repeat as needed.

For changes to the unit-expression grammar, update `GRAMMAR.md` and regenerate the derived grammar documentation as part of the build process.
